# Upgrading to 0.15

0.15 is a minor release, so under [VERSIONING.md](VERSIONING.md) it may change
behavior. Every change is listed here with the setting that restores the old
behavior. Where there is none, the old behavior was a defect or lost data, and
the entry says why.

Nothing changes without opting in for these new features: `accept-edits`,
`permissions` and `network` rules, `on_error`, `shell_env_passthrough`,
`prices`, `vision`, `buildwithnexus trust --print`, `--trust-project` /
`BWN_TRUST_PROJECT`, `--base-url`, `--worktree`, `--add-dir` and
`/add-dir`, agent files, `read_only` helpers, `idle_notify_secs`, `buildwithnexus update`, `buildwithnexus mcp login`,
`buildwithnexus acp` and the GitHub Action (`action.yml`).

## Install and update

| Change | To restore the old behavior |
|---|---|
| The npm launcher downloads the binary to `~/.buildwithnexus/bin/<version>/` (or `$NEXUS_HOME/bin/<version>/` when `NEXUS_HOME` is absolute) instead of the package's `bin/`. | `BWN_INSTALL_IN_PACKAGE=1`. For a noexec home, set `NEXUS_HOME` to an absolute path elsewhere or point `BWN_BIN` at a binary. |
| `"auto_update": "install"` installs patch releases only; a new minor or major is announced with its install command. | `"auto_update": "install-any"` in `~/.buildwithnexus/settings.json`. |
| The Windows exe links the C runtime statically. | Nothing to restore: it also runs where the Visual C++ Redistributable is installed. |
| Update notices say `run buildwithnexus update` instead of an npm command. `buildwithnexus update [--check]` is new and exits 10 when a newer release exists. | None needed. `BWN_UPDATE_REGISTRY` or `npm_config_registry` points the check at a mirror. |
| First launch no longer asks to install git, rg, node, npm or python3 and never runs `brew` or `sudo apt-get`. `buildwithnexus doctor` prints the install command for each missing tool and runs none. Session start mentions only a missing git. | None (security). Install the tools with your package manager. |
| A new file, `NEXUS_HOME/notices.json`, records which upgrade notices were shown, so each is shown once. | Delete the file to see them again. |

## Network

| Change | To restore the old behavior |
|---|---|
| `HTTPS_PROXY`, `HTTP_PROXY` and `ALL_PROXY` are honored (0.14 always connected directly). | `NO_PROXY='*'`, or list the hosts to reach directly in `NO_PROXY`. Loopback model servers are always direct. |
| Model servers on private, link-local, CGNAT (100.64/10) or IPv6 unique-local addresses, and host names that resolve only to them, connect directly even when a proxy variable is set, as with 0.14.10, which never used a proxy. Host names are resolved locally, with a 1 s cap, only when a proxy variable is set. | `BWN_PROXY_PRIVATE=1` sends them through the proxy. |
| A proxy variable that is not an `http://` URL (for example `socks5://`) makes the requests that would use it fail with an explanation. An `https://` proxy URL fails at once instead of after retries. | `NO_PROXY='*'`, or point `HTTPS_PROXY`/`HTTP_PROXY` at an `http://` proxy. |
| Certificates are checked against the OS store (or `SSL_CERT_FILE`/`SSL_CERT_DIR`) as well as the bundled roots. | `BWN_TLS_ROOTS=bundled`. |
| The web tools follow at most 5 redirects themselves and check each hop. | None needed: every redirect not aimed at a blocked address still succeeds. |
| `web_search` counts as network access to `lite.duckduckgo.com` and asks before sending a query outside `auto`, read-only mode included. | `"network": {"allow": ["lite.duckduckgo.com"]}` in `~/.buildwithnexus/settings.json`, or answer `a` once in a project. |
| `network` rules and approvals see the host a URL reaches: percent-escapes decoded and a trailing dot dropped (`https://%6Cite.example./` is `lite.example`), and a default port written out (`:443` on https) is left off. | None (security fix: `network.deny` could be stepped around by spelling the host differently). An approval saved for `host:443` asks once more. |

## Folder trust

| Change | To restore the old behavior |
|---|---|
| A project's `.buildwithnexus/system.md` applies only after you trust the folder, and is appended to your own `system.md`. | `"project_system_prompt": "replace"` in `~/.buildwithnexus/settings.json` lets a trusted project's file replace yours. The trust requirement has no opt-out. |
| A project skill with the same name as a bundled or user skill loads as `/project:<name>`. A project `skill_dirs` entry counts as the project's own, even as an absolute path. | `"project_skills_override": true` in your own settings (ignored in project settings), or add the directory to `~/.buildwithnexus/settings.json`. |
| A repository's own instruction files (AGENTS.md, CLAUDE.md) are asked about once per folder and content at startup (not when prompts are piped in, which only note them): `r` shows them, Enter uses them and is remembered in `NEXUS_HOME/notices.json`, Esc asks again next launch. A trusted folder is asked once too, since the trust prompt never showed these files. Until then a headless run prints one stderr line, `instructions from this repo: … (not reviewed — …)`, instead of a stdout line. | None needed: the files are used as before, and one Enter per folder silences the question. `"instruction_files": []` stops loading them. |
| Folders trusted before 0.15 are asked about again once if their hooks or MCP servers run repo files, call npm/make/just (in any subfolder), name a file by a bare word, or if the folder has a `.buildwithnexus/system.md`. | None: the trust record now covers those files. Answering the prompt once re-trusts the folder. |
| The trust prompt asks separately about a repository's `base_url` and `permission`, and a "no" is remembered for that file version. Existing `trusted.json` entries (plain digests) keep full trust. Older bwn versions read the new `{"digest","declined"}` entries as untrusted and ask again. | None needed. Answer yes to each question to trust the whole file as before. |
| A trusted project hook whose script changes mid-session is asked about in the terminal UI, or skipped with a warning in a headless run. | Trust the folder again. In CI, `--trust-project <digest>` (from `buildwithnexus trust --print`) trusts exactly the current content. |
| Project command folders (`.buildwithnexus/commands`, `.claude/commands`) and agent folders (`.buildwithnexus/agents`, `.claude/agents`) load only in a trusted folder, and a project's `prices` apply only once it is trusted. | New in 0.15; nothing to restore. |
| The repository's skills (`.buildwithnexus/skills`, `.claude/skills`, `.agents/skills`, and project `skill_dirs`) load only after you trust the folder. The repository's commands, skills and agent files are listed in the trust prompt and in `buildwithnexus trust --print`, and trust is pinned to their exact content: adding, editing or removing one asks again. A repository with only a command file now gets the prompt. Until then a notice names them and how to trust them. | None (security). Answer `y` at the prompt once, or use `--trust-project` in CI. |
| A `--trust-project` digest made before this change no longer matches in a folder with repository commands, skills or agents, because the digest now covers them. | None (security). Run `buildwithnexus trust --print` again for the new digest. |
| Repository command and agent files that are symlinks pointing outside their folder no longer load, and a repository script command must be a file inside its folder. | None (security). |

## Permission gate

| Change | To restore the old behavior |
|---|---|
| Windows-form sensitive paths (backslashes, drive letters, UNC, 8.3 names, wildcards, `-Path:value`) prompt. | None: skipping the prompt was a defect. Answer `s` or `a` for a specific command. |
| Windows destructive commands (see the CHANGELOG) and `rm -rf` on a drive path prompt even in auto mode. Some ordinary uses such as `rd /s /q build` or `bcdedit /enum` prompt too. | None: they are gated like `rm -rf /`. Answer `y` to let one through. |
| A permission switch typed in the conversation ("use auto") and `/permissions <mode>` last for the session and no longer write settings.json. | `/permissions default <mode>`, or "save as default" in the `/permissions` picker. |
| `s` and `a` answers for `rm`, `mv`, `cp`, `ln`, `chmod`, `chown`, `chgrp`, `dd`, `truncate`, `kill`, `pkill`, `killall` (and their Windows forms) cover that exact command. Approvals saved before still work. | To allow every call of such a program, add it to `allowed_commands`, or add a rule such as `"permissions": {"allow": ["run_command(rm *)"]}`. |
| `s` and `a` answers for destructive git commands cover that exact command: `git rm`, `git clean`, `git checkout`, `git restore`, `git filter-branch`, `git filter-repo`, `git prune`, `git update-ref`; `git reset --hard/--merge/--keep`; `git push` with `--force`, `-f`, `--force-with-lease`, `--delete`, `--mirror`, `--prune`, a `+ref` or a `:ref`; `git branch` and `git tag` deleting, forcing, moving or copying; `git switch --discard-changes/--force`; `git stash drop/clear`; `git reflog expire/delete`; `git worktree remove/prune`; `git submodule deinit`; `git notes remove/prune`; `git read-tree --reset/-u`; `git checkout-index --force`; `git gc --prune`. A saved approval for the subcommand (`git push`) no longer covers these forms; a saved bare `git` still covers every plain git command. Git's own options before the subcommand (`git -C dir status`) no longer become the key (it was `git dir`). | To allow every call of such a form, add a rule such as `"permissions": {"allow": ["run_command(git push --force*)"]}`. |
| `s` and `a` answers for wrappers that run the command after them (`fakeroot`, `firejail`, `bwrap`, `torsocks`, `proxychains`, `numactl`, `chronic`, `systemd-inhibit`, `ssh-agent`, …) cover that exact command, as for `env` and `sudo`; a saved bare approval of one is ignored, as for interpreters. | None (security fix): `s` on `fakeroot ls` approved `fakeroot rm -rf ~`. An allow rule such as `"permissions": {"allow": ["run_command(fakeroot make*)"]}` covers a family of calls. |
| Esc or Ctrl+C at an approval prompt ends the turn instead of returning the refusal to the model. | Answer `d <reason>` to refuse and let the model carry on. |
| Esc or Ctrl+C at a question the model asks stops the turn; the question's default is no longer sent as your answer. | Answer with text to let the model continue; Enter on an empty line still takes the default. |
| `"permission": "acceptEdits"` (or `accept-edits`) means the new accept-edits mode, which applies file edits only; it used to mean auto. | `"permission": "auto"`. |
| An unknown `--permission-mode` exits 2. An unknown `permission` value in settings warns and uses ask (it was silently ask before). | None: use ask, accept-edits, auto or readonly (`plan` reads as readonly). |
| The command given to `check_work` or `start_server` goes through the sensitive-path and dangerous-command checks even in auto, so `check_work` with `cat ~/.ssh/id_rsa` asks first. | None (security fix). |
| A `permissions` rule naming `run_command`, `bash` or `Bash` also covers the commands of `check_work` and `start_server`. | None (security fix). A rule that names `check_work` or `start_server` applies to that tool only. |
| Provider keys (`*_API_KEY`, `*_API_TOKEN`, `HF_TOKEN` and the other preset key variables) are removed from the environment of commands the agent runs, even without the sandbox. In a tmux server that was already running, `start_server` starts its command as `env -u <key names> sh -c '…'` (sh, not tmux's default shell). Hooks keep their environment. | List the variables a build or server needs in `"shell_env_passthrough"`. |
| A deny rule or a `network.deny` entry ends a headless run with exit 3 (`approval_blocked`). | No change unless you add these settings. |
| Deny and ask rules for shell commands see through wrappers (`env`, `sudo`, `nice`, `command`, `time`, `timeout`, `xargs`, `exec`, `eval`, `find -exec`, `fakeroot`, `firejail`, `uv run`, `bundle exec`, `FOO=1`, a path such as `/usr/bin/git`), into `sh -c`, `bash -lc`, `cmd /c`, `pwsh -Command`, `$(…)` and backquotes, past git's options before the subcommand (`-C`, `-c`, `--git-dir`, `--work-tree`, `--attr-source`), through an alias given with `-c alias.<name>=…`, and to git's own `git-<command>` programs. A deny rule also refuses a pipeline or compound command that names its program anywhere, such as `cargo fmt && git status` under `run_command(git push*)`, and likewise code handed to an interpreter (`perl -e 'system "git push"'`) or a word in bash's `$'…'` quoting. On Windows the rules read a command as cmd.exe passes it on (`g^it push` is `git push`), and a command with `^` or `%` counts as compound. | None (security fix): these forms stepped around the rules. Run the command on its own instead of in a compound command; allow rules are unchanged. |
| `apply_patch` (and `patch`) is checked for each file its diff names: `permissions` rules naming paths, the sensitive-path prompt (`.env`, `~/.ssh` and the rest, even in auto), accept-edits (a patch into `.git` asks) and hook guards (`tool_input.file_path`, once per file). Before, a patch named no file, so it stepped around all of them. | None (security fix). |
| `move_path` is checked on the paths it moves, with surrounding spaces removed as the tool removes them; a move to `" ../x"` is refused as outside the working folder and a move onto `".env "` asks. | None (security fix). |
| The legacy `mcp_call` tool is checked as the MCP tool it calls (`mcp__<server>__<tool>`): its hooks, `permissions` rules, saved approvals and read-only hint apply. | None (security fix): name the `mcp__…` tool in rules and matchers. |
| A write outside the working folders (`../x.txt`, a link out of the project) is refused by the tool without an approval prompt first; the prompt's `y` or `s` could not let it through. | None (defect). Add the folder with `/add-dir` or `--add-dir`. |
| `s` and `a` at a sensitive-path prompt (`.env`, `~/.ssh` and the rest) cover that path, and the legend names it (for example `access /proj/.env`); they used to name the tool or command, which a sensitive path asked about again anyway. A saved `access <path>` approval then lets that path through to the usual checks. | None needed: the old answer did not skip the next sensitive-path prompt. |
| Starting a helper with `read_only: true` (`task` or `spawn_subagent`) is a read: ask mode starts it without a prompt, and read-only mode, which now offers `spawn_subagent`, runs it (any helper started in read-only mode is read-only). The helper is still refused every change. | Leave out `read_only` to have ask mode prompt for the helper. |
| Esc at an approval prompt prints one line, `✗ stopped by the user — ask what to do instead`; the second line `stopped — tell me what to do instead` is gone. | None (duplicate line). |

| A hook matcher naming the shell (`Bash`, `run_command`, `bash`) also applies to `check_work` and `start_server` calls that carry a command. | None (security): a shell guard could otherwise be stepped around. |
| `PreToolUse` and `PermissionRequest` hooks run once per file for `move_path` (source and destination), `read_many_files` and `apply_patch`. | None: a guard reads one `file_path`, so it must see each file. |
| `tool_input` in hook payloads gains Claude Code's field names next to bwn's (`file_path`, absolute, `old_string`, `new_string`, `content`, `prompt`, `subagent_type`, `glob`, `path`, `todos`), and `Stop` payloads gain `stop_hook_active`. | None needed (fields are only added). |
| Headless ask mode with a `PermissionRequest` or `PreToolUse` hook warns that only the calls those hooks do not allow will be blocked, instead of that every edit and command will be. | None (wording). |

## Release process (maintainers)

- `publish.yml` has no `version_bump` input; a dispatch with no inputs
  re-publishes the current version. Bump versions in a PR to main.
- GitHub releases stay drafts until every asset is attested and uploaded; the
  tag is created when the draft is published.
- `publish.yml` installs the exact npm tarball in clean containers before
  publishing it, and stops on any failure.
